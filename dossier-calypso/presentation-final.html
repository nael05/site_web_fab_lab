4. La démonstration, point par point (partie 5 du sujet)

Point 1. Le schéma (1 min)

Afficher le schéma de la section 2 et dire les trois zones, le tunnel et Netdata.

Point 2. Le tunnel : wg show sur les deux extrémités

ssh gw "sudo wg show"
ssh agence "sudo wg show"

Montrer : « latest handshake » récent, allowed ips (gw : 10.10.99.10/32 + 10.10.30.0/24 pour l'agence ; 10.10.99.2/32 pour nomade), systemctl is-enabled wg-quick@wg0 = enabled.

Point 3. Les flux de l'agence : un autorisé, un refusé, la ligne du journal

Dans ssh agence :

ping -I 10.10.30.1 -c1 10.10.10.10                                   # autorisé : 1 received
curl -s -o /dev/null -w '%{http_code}\n' --interface 10.10.30.1 http://10.10.20.10   # autorisé : 200
nc -zv -w3 -s 10.10.30.1 10.10.10.10 22                              # refusé : timed out

Puis sur gw la ligne du journal :

ssh gw "sudo journalctl -k --since -2min | grep gw-forward-drop | tail -1"

Lire la ligne : IN=wg0 (arrive par le tunnel), OUT=ens37 (vers le LAN), SRC=10.10.30.1, DST=10.10.10.10, DPT=22, SYN (début de connexion) : refusé par la politique drop, car aucune règle F15 à F19 ne l'autorise.

Point 4. Netdata : tableau de bord, alertes, historique de la panne

ssh -L 19999:127.0.0.1:19999 srv        # laisser ouvert
http://127.0.0.1:19999   →  « Skip and use the dashboard anonymously »  →  Alerts, puis Events

Montrer l'historique de ping_host_reachable (agence) : CRITICAL à 10:59:15, CLEAR à 10:59:45. Panne en direct si le temps le permet (CRITICAL en environ 40 s) :

ssh agence "sudo systemctl stop wg-quick@wg0"      # panne

5. Questions individuelles : réponses courtes

QuestionRéponse
Pourquoi le pair agence a-t-il deux réseaux dans ses AllowedIPs côté gw, et nomade un seul ?L'agence est un routeur : son adresse de tunnel (10.10.99.10/32) plus le réseau derrière elle (10.10.30.0/24). Nomade est un poste seul : 10.10.99.2/32.
Un paquet de l'agence vers web : quelles chaînes de gw ? Est-il traduit ?prerouting (rien : le DNAT ne vise que le WAN), forward (règle F18), postrouting (le masquerade ne s'applique qu'à la sortie WAN). Pas de NAT : web voit 10.10.30.1.
Le tunnel tombe : que voit Netdata, quelle première commande ?ping_host_reachable passe en CRITICAL (et le port 22 de l'agence échoue). Première commande : sudo wg show des deux côtés, puis journalctl -k | grep 51820 sur gw.
Pourquoi le tableau de bord n'écoute-t-il que sur 127.0.0.1 ?Il n'a pas d'authentification : on ne l'expose pas. On y accède par un tunnel SSH, authentifié et chiffré.
Comment l'agence résout-elle intranet.calypso.internal ? Et si srv est éteint ?Via le DNS de srv (10.10.10.10) par le tunnel (F16, ACL de bind9 incluant 10.10.30.0/24) : un CNAME vers web (10.10.20.10). Si srv est éteint : plus de résolution ni de proxy ; seules les adresses IP restent joignables.
Si on ajoutait un poste dans l'agence, que faudrait-il de plus sur agence ?ip_forward activé, DHCP (ou adresse fixe) avec agence en passerelle et srv en DNS, règles de transfert sur agence. Côté gw rien : 10.10.30.0/24 est déjà dans les AllowedIPs et dans la variable AGENCE.
Netdata supervise-t-il le VPN ?Indirectement : il surveille l'agence par le tunnel (ping de 10.10.30.1 et port 22), donc une panne du VPN déclenche une alerte. Il ne lit pas l'interface wg0 elle-même (pas de collecteur WireGuard sur gw) : une piste d'amélioration.

6. Limites et suite

  • Pas de redondance (un gw, un tunnel, un DNS) ; sauvegardes manuelles ; pas de poste réel dans l'agence ; pas de notification d'alertes.
  • SSH ouvert sur le WAN de gw (F2), à remplacer par le VPN.
  • Accès temporaires du lab à supprimer : sudo sans mot de passe et clé SSH sans phrase de passe sur srv.
